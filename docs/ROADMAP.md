## Release 2.0 — 感知层（当前）

范围：**仅感知层 + 弹幕出口**。
帮助层不做。
每个 Milestone 结束有确认门（⏸），需要用户确认后才进入下一个。

- 配置文件（storage_bytes、daily_requests可选、effort、K/M/N、节流、模型路由）——全部为弹性输入，引擎推导运行参数
- ⏸ **确认门：schema 评审**——六张表（DESIGN §10.G1 三表合一 + M0 定稿纳入 metrics）的字段定稿，之后改表要迁移【已确认 2026-09-18】

### M1 传感器（L0）
- 屏幕采集（x11grab）+ pHash 门控 + 空帧拦截 + 大事件检测（封闭枚举：窗口切换/workspace/全屏/恢复空闲）
- 采样节奏控制器：动力学EMA分档（60s/20s/2s+批帧），大事件直通
- 活动窗口标题采集；捕获排除清单生效（若 Q1 决定启用）
- ⏸ **确认门：实跑一天**，检查事件流的召回/误报率（同时报告：捕获排除清单命中次数，若启用）

## Release 3.0 — 见证者

Release 3.0 是主线：先把"能见证且能被证伪"做出来，而不是先把帮助做出来。
这条主线的段按序是 gather data → observe/collect → analyze/reason → verify → offer → get supervised → take over。
其中 get supervised（受监督）由 M4b 覆盖，门槛是撤销率 ≤10% 与无回归（既有 check 全绿）。
证据的组织方式是五条取证通道并行取证，每条通道有自己的判官；跨通道只做汇总，不发明一个平均分。
痛点与证据住在 [PAIN.md](PAIN.md)，可观测事实闭集、证据引用、labels 契约与各门槛的判定口径住在 [SCHEMA.md](SCHEMA.md)，本文只写里程碑结构。

### 五条取证通道（A–E）

这里的通道是一条独立取证通道，它有自己的输入、判官与退出判据；它与本文 Release 2.0 的层名 L0 传感器 / L1 见证 / L2 金字塔 / L3 深潜无关，也与弹幕出口的排位 lane 无关。

| 通道 | 输入 | 判官（oracle） | 服务的段 | 不能支持什么 | 够用判据 |
|---|---|---|---|---|---|
| A 自有历史 | 自有记录（评测前冻结成快照；当前计数见 [PAIN.md](PAIN.md) 证据节） | 与原始流一致：语义字段可回指到 observations | analyze/reason 与 verify | 不能证明采集面够宽（只有 screen 一种）；不能证明跨域泛化 | D1 通过（A 达 100% 且 B ≥95%），且同一记录重放得到相同语义字段 |
| B 自有时序事件流 | 本机正在发生的多传感器事件（屏幕、ATSPI、文件系统、git、进程、输入活跃度） | 事件捕获率 + 行为标签（labels 表，来自 pi 会话文件）【已定：labels 不进 M0′，迁移授权归 M1′，见 [SCHEMA.md](SCHEMA.md)】 | observe/collect | 它观察的多数时间是屏幕上的 agent 会话而不是人，人类行为仍然稀疏；不能替代用户亲自确认 | 行为标签一致率（分母＝ labels 中该题的行为条数）可被判官复算；事件捕获率的真值口径在 M0′ 交出时另定 |
| C 公开冻结轨迹 | 公开仓库的 issue→commit/PR→review 冻结轨迹 | 上游 CI 的机械结论（可回指上游日志） | analyze/reason 与 offer | 不能证明本地采集有效；合并率不是本产品的指标 | 每条结论都能回指上游 CI 记录，回指不了的样本不计入 |
| D 视频/音频 | 视频与音频输入（监听面，身份定义见 [DESIGN.md](DESIGN.md) §1） | 产物能否构建/运行 | 观察信号：是否有人在场、是否只有播放在响 | 押后，不能支持任何接管结论 | 未定（押后，启动时另立判据） |
| E 合成/已知缺陷环境 | 注入的已知缺陷与已知答案的环境 | 已知答案，由环境本身持有 | take over | 不能证明真实任务上的接管；合成环境不会自行老化 | 与已知 oracle 一致率 100%，任一步偏离即该次不算通过 |

每条通道在 M0′ 结束时要交出接入器、判官与自己的退出判据；退出判据的写法是把这条通道关掉，剩下的结论仍能被别的通道复算的那部分才算已经退出。

**M1′ 跨域评测矩阵**

- 交付：同一语义层在 A/B/C/E 上跑短程语义状态预测，报每通道结果与泛化 gap，不给平均分。
- 基线必须含：只看当前帧、只看事件序列（`window_switch` 的 key 序列；observations 无标题列，窗口标题只作该事件的 key）、直接 grep 原始表、现行 `--stats`。
- 判官：各通道判官各自复算，判官之间不折算。
- 门槛（建议值，待真实数据校准）：语义状态预测准确率相对最强基线 ≥+15 绝对点、引用正确率 ≥95%、跨重启一致率 ≥90%；绝对点、准确率与引用正确率按 [SCHEMA.md §门槛判定程序](SCHEMA.md#门槛判定程序) D2 判定，跨重启一致率按 D6 判定。
- 失败判据：任一项低于门槛，或某条通道只报平均分不报分项，或留出集被用于调参（切分契约见 [SCHEMA.md](SCHEMA.md)）。

**M2′ 证伪与弃权校准**

- 交付：扰动测试（打乱时序、替换窗口/事件 key、插入无关帧、截断历史）的敏感度、长程臂 T+N 意图摘要、弃权校准。
- 判官：扰动必须能被检出，长程摘要必须能被记录核对，评审本身要用故障注入（埋雷）测量。
- 门槛：扰动敏感度 ≥80%、过度自信率 ≤5%；扰动敏感度按 [SCHEMA.md §门槛判定程序](SCHEMA.md#门槛判定程序) D7 判定，过度自信率按 D3 判定（不产出逐题置信则该里程碑判不通过）。
- 失败判据：扰动后结论不变、长程臂无法被记录核对、或过度自信超过门槛；允许负结果，负结果照实记录。

**M3′ 有据的提议（dry-run，不落地）**

- 交付：提议只写不执行，每条提议 5 秒内可被记录证实或否证。
- 判官：前提蕴含 + 埋雷测过的独立评审，评审只依赖独立批判 subagent。
- 门槛：可核对率 100%、埋雷捕获率 ≥80%、误杀率 ≤10%；可核对率按 [SCHEMA.md §门槛判定程序](SCHEMA.md#门槛判定程序) D5 判定，埋雷捕获率与误杀率按 D8 判定。
- 失败判据：存在无法在 5 秒内被判定的提议、埋雷没被捕获、或误杀超过门槛。
- 本里程碑不解锁任何执行权。

**M4a 合成环境接管闭环（先做）**

- 交付：在已知 oracle 的环境里跑通 observe 到 take over 的闭环。
- 判官：已知 oracle；动作在后台进行、不阻塞用户、可回滚、留证据链。
- 门槛：与 oracle 一致率 100%、回滚准备 100%、对用户的阻塞时间 0（三项判官都是全称判断，逐项全对才算通过）；本行即其判定口径，索引见 [SCHEMA.md §门槛判定程序](SCHEMA.md#门槛判定程序)。
- 失败判据：任一步与 oracle 不一致、动作不可回滚、或占用了用户的前台注意力。

**M4b 真实维护类接管台账（后做，30 天真实运行）**

- 对象限定：用户一直欠着且有既有 check 的维护类工作——依赖、文档漂移、死链、长期红的测试、备份。
- 判官：既有 check + 事后采集的行为标签。
- 门槛：撤销率 ≤10%、无回归（既有 check 全绿）；撤销率与无回归按 [SCHEMA.md §门槛判定程序](SCHEMA.md#门槛判定程序) D4 判定。
- 失败判据：撤销率超过门槛、既有 check 出现回归、或动作阻塞前台/不可回滚。
- 时间跨度【待用户确认】：30 天是当前记录的值。

**M5′ 公开仓库 offer（并行可选）**

- 交付：对公开仓库发出的 offer，先审后发。
- 判官：上游 CI 机械通过率。
- 门槛：先审后发 100%、未审即发路径在本地伪造上游上被检出 100%、上游 CI 通过率 ≥90%（第三项是建议值，待真实数据校准）；本行即其判定口径，索引见 [SCHEMA.md §门槛判定程序](SCHEMA.md#门槛判定程序)。
- 失败判据：任一条未经审阅就发出、未审即发路径没被检出、CI 结论回指不到上游日志；合并率不作为指标。
- 失败暴露方式：先在本地伪造上游仓库（oracle＝拒收）上跑"未审即发"路径，该路径的检出是门槛的一部分，不拿真实公开仓库当试验场。

### 组合漏洞条款

- 组合证据不等于端到端成立：每段都过，合起来仍然可以失败。
- 每个里程碑都要附已知缺口清单，缺清单不算交付。
- 必须主动寻找"每段都过但整体失败"的阴性对照。
- 在找到这种阴性对照之前，任何文档不得写"已验证接管"。

## Release 3.x — 帮助层（北极星第一阶段）

方法论（落地前单独成文打磨）：

1. **提案流**：画像层检测重复模式（同一动作序列≥N次无失败）→ 生成提案 → **必须用户确认**——"我发现你经常这么干，你想达成的是不是X？我能做个工具帮你，方案是这样，行不行？"
2. **分级阐述**：按用户背景调整表达——非程序员/小孩听得懂的方案描述；细节谁定（系统定 or 用户定）由用户专业度路由
3. **执行**：批准后由执行后端完成（自研只读/白名单工具循环起步；agent 框架适配器可选）
4. **回访**：执行后主动回访效果，"好不好用"，结果写回画像
5. **垂直开发纪律**：需求追踪、业务理解落盘、设计/开发/调试原则、agent spawn policy——参考 AGENTS.md 方法论，形成 Backseat 自己的 `help-policy` 文档
